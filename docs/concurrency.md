# 并发模型深度专题

> Java 后端开发者最关心的对比维度。五门语言的并发模型本质差异是什么？如何正确使用？有哪些坑？

---

## 1. 各语言并发模型概述

### Java：线程池 + 锁 + CompletableFuture

```
┌─────────────────────────────────────────┐
│  JVM 线程池                              │
│  ┌───┐ ┌───┐ ┌───┐        ┌───┐         │
│  │ T1│ │ T2│ │ T3│  ...   │ Tn│  平台线程 │
│  └───┘ └───┘ └───┘        └───┘         │
│  synchronized / Lock / AtomicLong        │
│  CompletableFuture (异步组合)             │
└─────────────────────────────────────────┘
```

- 基于操作系统线程（1:1）
- 线程创建成本高（~1MB 栈内存）
- 必须用线程池限制并发数
- 锁竞争可能成为瓶颈
- `CompletableFuture` 提供异步链式调用

### Go：Goroutine + Channel（CSP 模型）

```
┌─────────────────────────────────────────┐
│  Go Runtime (GMP)                        │
│  G: Goroutine (轻量，几KB栈)              │
│  M: OS Thread                            │
│  P: Processor (调度器)                    │
│                                          │
│  G1 ←→ channel ←→ G2                    │
│  G3 ←→ channel ←→ G4                    │
└─────────────────────────────────────────┘
```

- 基于用户态线程（M:N）
- Goroutine 极轻量（初始 2KB 栈，可动态扩缩）
- 百万级并发轻松支持
- CSP 模型：通过 channel 通信，不通过共享内存
- `sync.WaitGroup` / `sync.Mutex` 作为补充

### Python：GIL + asyncio 协程

```
┌─────────────────────────────────────────┐
│  CPython GIL (全局解释器锁)               │
│  ┌─────────────────────────────────┐    │
│  │  任意时刻只有一个线程执行 Python   │    │
│  │  字节码                         │    │
│  └─────────────────────────────────┘    │
│                                          │
│  asyncio: 单线程协程，IO 密集高效         │
│  multiprocessing: 多进程绕过 GIL          │
└─────────────────────────────────────────┘
```

- **GIL 限制 CPU 密集型任务的多线程并行**
- `asyncio` 协程：单线程 + 事件循环，IO 密集高效
- CPU 密集需用 `multiprocessing`（进程间通信成本高）
- FastAPI / aiohttp 都是基于 asyncio

### Rust：tokio 多线程运行时 + 编译期防竞态

```
┌─────────────────────────────────────────┐
│  Rust Tokio Runtime                      │
│  ┌───┐ ┌───┐ ┌───┐                      │
│  │ T1│ │ T2│ │ T3│  多线程工作窃取调度器  │
│  └───┘ └───┘ └───┘                      │
│                                          │
│  所有权系统 + Send/Sync trait             │
│  → 编译期禁止数据竞争                      │
└─────────────────────────────────────────┘
```

- 编译期保证线程安全（所有权 + Send/Sync）
- `tokio` / `async-std` 异步运行时
- `std::thread` 原生线程
- 无数据竞争 = 无锁竞争 = 高性能并发

### TS(Node)：单线程事件循环 + Promise

```
┌─────────────────────────────────────────┐
│  Node.js Event Loop                      │
│  ┌──────────────────────────────────┐   │
│  │  单线程 JS 执行                    │   │
│  │  ┌─┐┌─┐┌─┐┌─┐                    │   │
│  │  │P1│P2│P3│P4│ Promise 链         │   │
│  │  └─┘└─┘└─┘└─┘                    │   │
│  └──────────────────────────────────┘   │
│                                          │
│  线程池 (libuv): 文件 IO、加密等          │
│  worker_threads: CPU 密集任务             │
└─────────────────────────────────────────┘
```

- 单线程 JS 执行 + libuv 线程池处理系统调用
- `Promise` / `async-await` 异步编程模型
- 天然避免数据竞争（单线程）
- CPU 密集任务需要 `worker_threads` 或 child process

## 2. 并发模型对比表

| 维度 | Java | Go | Python | Rust | TS(Node) |
|------|------|----|--------|------|----------|
| 线程模型 | 1:1 平台线程 | M:N 用户态 | GIL + 协程 | 原生线程 + 异步 | 事件循环 |
| 创建成本 | 高（~1MB） | 极低（~2KB） | 低（协程） | 中 | 极低 |
| 百万级并发 | 需调优 | 轻松 | 仅 IO 密集 | 轻松 | 轻松 |
| CPU 密集 | 多线程并行 | 多核心并行 | **GIL 阻塞** | 多线程并行 | 需 worker_threads |
| 数据竞争 | 锁保护 | channel 优先 | GIL 天然避免 | **编译期禁止** | 单线程避免 |
| 异步方案 | CompletableFuture | channel | asyncio | tokio | Promise |
| 调试难度 | 中 | 低 | 低 | 高（所有权） | 低 |

## 3. 常见坑

### Java 开发者容易在 Go 踩的坑
- ❌ 用 Java 思维创建大量线程 → Go 用 Goroutine，数量级不同
- ❌ 依赖 synchronized → Go 推荐 channel 通信
- ✅ 但也别滥用 channel，简单共享数据用 sync.Mutex 更高效

### Java 开发者容易在 Python 踩的坑
- ❌ 以为多线程能并行计算 → GIL 让 CPU 密集任务串行
- ❌ 用 ThreadPoolExecutor 处理 CPU 密集 → 改用 ProcessPoolExecutor

### Java 开发者容易在 Rust 踩的坑
- ❌ 尝试在线程间传引用 → Rust 所有权不允许
- ✅ 用 Arc<Mutex<T>> 或消息传递
- ❌ 在 async 任务里持 `MutexGuard` 跨 `.await` → 编译期不报错但运行时死锁（std 的锁不是 async-aware）
- ✅ 用 `tokio::sync::Mutex`，或把临界区缩到不含 `.await` 的同步块内

### Java 开发者容易在 TS(Node) 踩的坑
- ❌ 以为 `Promise.all` 能限流 → 它会**同时发起全部请求**，瞬间打满下游
- ✅ 需要并发上限时手写队列，或用 `p-limit` 之类的库
- ❌ 在事件循环里做 CPU 密集计算 → 阻塞整个进程，所有请求一起变慢
- ✅ 挪到 `worker_threads` 或独立服务

### 跨语言的共同坑
- ❌ 忽略"并发数"这个变量做性能对比 → 测的是"谁敢开得多"，不是"谁的并发模型好"
  （本仓库场景 02 强制所有语言都接受 `concurrency` 参数，就是为了消除这个偏差）
- ❌ 用 IO 密集 benchmark 去证明 CPU 密集场景的结论 → 两类场景的排名可能完全相反
- ❌ 在容器里测吞吐却不设 CPU limit → 结果与宿主机构型强绑定，换个机器就不可复现
